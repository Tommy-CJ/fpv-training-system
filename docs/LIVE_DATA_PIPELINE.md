# 实时训练核心数据链路

本文档定义训练系统的数据所有权、一致性边界和不可破坏的实现约束。修改串口、WebSocket、IndexedDB、SQLite、条带或统计前必须先阅读本文，并运行文末验证。

> 当前验收记录（2026-09-23）：用户在新打开的浏览器页面/窗口中实测，正常联网条带连续、断网恢复速度快，飞行状态断网后重建也正常。本次场景已通过现场观察；这不等于浏览器整页冻结、操作系统睡眠、USB 拔出等极端场景获得了不丢数据保证。后续修改仍须重新验证，不得用状态延时保持或伪造连续区间掩盖真实缺口。

## 0. 变更控制：这是受保护的稳定核心

本链路来自长期真实环境调试，解决过串口分帧、后台缓冲、部分接收机批次、在线低延迟、IndexedDB可靠性、ACK去重、断网回补、事件归属、接收机迁移、时间线重建以及教练端/观众端一致性等相互耦合的问题。后续开发者和AI必须把这里的职责边界视为兼容性契约，而不是可以顺手整理的实现细节。

默认允许的改动：

- 新页面、新指标、AI分析和导出功能以只读消费者或旁路方式读取现有权威结果；
- 在不改变消息语义、采样频率、ACK时机和数据所有权的前提下增加诊断、测试或有界保护；
- 对恢复支路做有专项证据的最小修复，同时保持当前实时流严格优先。

未经用户明确授权，禁止：

- 合并、拆分或替换30Hz实时流与约5Hz可靠帧；
- 恢复独立的在线 `persistOnly` 双发流，或让回补旧包进入当前实时广播；
- 绕过“IndexedDB提交后发送、服务器处理后ACK、ACK后删除”的顺序；
- 把SQLite权威历史改成浏览器永久推算结果，或让教练端与观众端分别维护真相；
- 把飞行规则改成绝对油门、摇杆偏移、客户端状态、延时保持或其他启发式规则；
- 以重构、性能优化、减少代码量或统一状态管理为理由改变接收时间、事件归属、接收机迁移、1秒真实缺口、回补收尾和完整基线语义；
- 在没有专项测试与真实环境回归计划时修改 `TrainingSystem.jsx`、`liveOutbox.js`、`livePersistence.js`、`serialJsonStream.js`、`server.js`、`server/live/sampleProcessing.js`、`server/features/training/createTrainingRuntime.js` 中的数据链路代码。

任何跨越上述边界的方案必须先写出：当前行为证据、拟改变的契约、兼容与迁移方案、故障回滚方案，以及本文第7节的自动和真实环境验证结果。不能凭局部代码观感直接实施。

## 1. 三层职责

### 实时显示层

- 接收阵列通过 Web Serial 向教练端发送 `rx_batch`。
- 串口读取与完整 JSON 结构分帧必须运行在 Dedicated Worker；页面渲染、React 更新、`requestAnimationFrame`、可见性和后台定时器不得承担采集职责。Window 线程只能消费 Worker 已经标注采集时间的完整帧。
- 串口读取块和换行都不是消息边界；必须按完整 JSON 结构分帧。Web Serial 的 overflow/framing/parity 等非致命错误会产生新的 `ReadableStream`，读取端必须释放旧 reader 后立即继续读取，不能关闭串口再等待页面定时器重连。
- `rx_batch.t` 是接收阵列的单调毫秒时钟。若浏览器/操作系统缓冲后一次吐出多帧，必须用它保持原帧间隔；严禁给整批积压帧统一赋恢复瞬间的 `Date.now()`。
- 教练端直接使用本机串口数据显示当前摇杆和当前状态。
- 教练端以约 30Hz 将最新帧发送到 `/live-ws`；服务器只向观众转发最新画面，不补播已经错过的实时帧。
- 历史回补包严禁广播成当前实时画面。

### 可靠历史层

- SQLite `training_samples` 是历史样本的权威账本。
- 在线时仍然只有一条30Hz实时消息流；约每200ms选中的一帧增加 `durable + packetId + eventId + clientSequence`，同一份消息同时承担实时广播和约5Hz可靠落库。
- 被选中的可靠帧必须先写入浏览器 IndexedDB，再通过 WebSocket 发送。
- 服务器完成去重、事件/飞手映射和 SQLite 处理后才返回ACK。
- 浏览器只有在收到成功ACK并完成 IndexedDB 删除事务后，才允许移除本地记录。
- 普通实时帧仍可作为服务器自主抽样的兼容兜底，但不得产生第二份在线 `persistOnly` 流。

### 权威展示层

- 教练端和观众端的完整历史条带与累计统计最终都以服务器 SQLite 为准。
- 正常直播期间，服务端每秒发送统计和最近条带增量；前端只把增量接到已有完整基线上。
- 首次进入、刷新、重连、页面重新可见、配置/接收机归属变化、回补完成时，必须取得一次完整权威历史。
- 完整REST结果不能被重连前或回补前的旧 WebSocket 基线重新覆盖。
- 教练端可用30Hz本地数据补画尚未落库的短尾部，但不能用本地推算永久替代SQLite历史。

## 2. 在线主链路

```text
接收阵列
  -> Web Serial结构化分帧
  -> 教练端本地30Hz显示
  -> 30Hz live_batch
       |- 普通帧：仅实时广播，服务器可兜底抽样
       `- 每约200ms可靠帧：先写IndexedDB，再发送durable帧
             -> 服务器广播当前画面
             -> 去重、按当前配置映射
             -> SQLite约5Hz落库
             -> ACK
             -> 浏览器删除IndexedDB记录
```

不可破坏的在线约束：

1. 恢复旧历史不得阻塞当前实时帧。
2. 在线可靠帧不得再额外复制成一份 `persistOnly` 消息。
3. 服务器使用接收时间作为在线历史时间，不能让客户端未来时间污染5Hz游标。
4. 单个硬件包可能只包含部分接收机；可靠帧必须使用浏览器维护的各接收机最新值快照。
5. 当前接收机配置是在线数据的映射依据。
6. 队列只允许合并不带 `packetId` 的普通30Hz兜底帧。已经进入 IndexedDB 的可靠帧不能被后来的可靠帧覆盖，更不能在服务器尚未处理时返回 `accepted: true`；可靠帧必须保持到达顺序并排在回补队列之前。
7. **回补身份只能来自协议显式标记。** 只有浏览器从 IndexedDB 重放且明确携带 `backfill: true` 的包才能进入回补队列、使用客户端采集时间、发布渐进补丁或触发最终重建。服务器严禁根据 `clientTime` 年龄、传输延迟、客户端与服务器时钟差、页面是否后台、处理耗时或 ACK 快慢，把普通在线可靠帧推断成回补包。
8. 正常联网时，即使浏览器/IndexedDB/CSV/服务器发生秒级抖动，`累计恢复`、`渐进`、`校准`也不得因此增加；这些计数只能由显式回补代际推动。
9. 页面切到后台、被其他窗口遮挡或 `requestAnimationFrame` 暂停，不得停止串口读取。页面线程晚于采集时间3秒以上才收到的 Worker 帧必须只进入 IndexedDB 历史回补，禁止快放成当前摇杆或按恢复瞬间时间写入在线历史。
10. 后台采集期间，Window/React 不得按帧刷新串口状态、FPS或中继UI；采集、5Hz快照、IndexedDB和网络发送不依赖这些UI更新。重新可见时只显示最新状态，不得把后台积压摇杆逐帧播放一遍。
11. 串口占用声明的有效期必须覆盖 Chromium 的后台定时器降频，且页面重新可见/恢复时立即续约。`visibilitychange`、`pagehide` 和普通路由遮挡不得主动关闭串口。

## 3. 断网恢复支路

```text
网络不可用或ACK丢失
  -> 可靠帧保留在IndexedDB
  -> WebSocket恢复
  -> 当前30Hz与当前5Hz可靠帧优先
  -> 旧记录以 backfill + persistOnly 后台补传
  -> 服务器按原 clientTime 和当时接收机归属写入
  -> 每包ACK后删除本地记录
  -> 浏览器完成通知，或服务器检测回补静默收尾
  -> 一次性重建 segments / stats
  -> 广播完整新基线 + live_timeline_resync
  -> 教练端与观众端重新取得权威历史
```

恢复约束：

- 恢复代际以重连时的采集时间/序号截止点冻结；重连后产生的新帧不能让旧代际永远无法清空。
- 恢复发送泵有积压时约每25ms尝试一轮，服务器有回补队列时约每20ms主动排空，观众端约每500ms接收一次渐进历史更新。它们是当前恢复体验的基线，不是可以随意调大的“后台优化参数”；调整需同时测当前直播延迟、补传吞吐和渐进可见时间。
- WebSocket处于OPEN不代表服务器已收到；超过ACK超时的记录必须允许重发。
- 后台标签页的 Window 定时器可能已过截止时间仍未执行；收到 ACK、WebSocket 重连或页面恢复可见时必须能重新唤醒缓存发送泵，不得因旧定时器的过期截止时间而空等。
- 断网截止前已经排队的 IndexedDB 写入必须完成后，才能判定恢复代际为空。
- 旧记录使用原始采集时间，并按 `training_receiver_assignments` 查询当时的接收机归属。
- 回补期间只插入样本并标记重建，不得每补一包就全量重算。
- 回补状态判定只能读取该采集时刻的 SQLite 历史上下文；回补包不得覆盖当前在线飞手的最近5秒内存窗口、最新接收机状态或实时状态广播时钟。即使在线飞行与旧包交错，下一条在线样本的状态也必须沿用此前在线窗口。回补包不得为一份不会广播的实时状态做汇总查询。
- 服务器不得只依赖浏览器最后一条完成消息；回补流安静且队列清空后也必须能够收尾。
- 回补完成后必须广播新的完整基线。只发“请刷新”通知会允许旧重连快照再次覆盖REST结果。
- 普通在线可靠帧无论延迟多久都不能自动改道为回补；短时网络波动的数据恢复必须走浏览器 ACK 超时后的 IndexedDB 显式重放，不能由服务器猜测。
- Worker 已确认的后台积压帧属于唯一例外：它们由浏览器采集端根据硬件单调时钟确认原采集时间，再明确写入 IndexedDB 并以 `backfill: true + persistOnly: true` 重放；这仍然是协议显式回补，不是服务器延迟推断。

## 4. 条带和统计语义

- 飞行、待机、反乌龟使用同一批约5Hz权威样本计算。
- 飞行规则固定为 `armed && 最近5秒油门最大值与最小值之差 > 80`。浏览器不得上传 `armed/flying/turtle` 判定。约5Hz可靠帧可以附带每个接收机在本200ms窗口内真实出现过的最低/最高油门原始记录，服务器将其折算为同一SQLite行的 `throttle_min/throttle_max`；这是对原始30Hz极值的无损摘要，不是客户端状态判定，也不得借此提高SQLite行频率。
- 单个可靠帧携带的油门极值只可来自它附近有界的原始帧窗口（当前上限500ms）。串口时钟重置或页面调度停顿后，不得把几秒前的飞行动作混进新的待机帧；正常持续采样仍保留本200ms内的真实极值。
- 相邻样本间隔不超过1秒时，前一个样本状态覆盖到后一个样本时间。
- 超过1秒的真实数据缺口必须保留为空白，不能伪造连续飞行。
- 相邻同状态条带在服务端和前端都应合并；不得通过抽取“每N段”降低绘制量，那会制造假白缝。
- 飞手起止时间只影响利用率窗口，不得错误截断真实总飞行和反乌龟累计。
- 接收机迁移不改变飞手身份；迁移前后的样本通过历史归属合并到同一飞手。
- “距上次”显示使用单调页面时钟，不能在样本时间与 `Date.now()` 之间切换导致跳秒闪烁。

## 5. 诊断口径

- `当前队列 0/1`：正常200ms工作队列，不代表历史缺失。
- `最近当前包落库 0/N，限频 N`：这一候选包距离上次落库不足200ms，是健康限频，不是丢包。
- `浏览器断网缓存`：教练端 IndexedDB 的恢复状态；服务器离线时仍应可观察。
- `回补队列`：服务器某一瞬间尚未处理的包数，通常很快归零，不能代替累计指标。
- `回补累计处理/落库/跳过原因`：判断缓存包是否真正补进权威历史。
- `最近重建`：服务器完成 segments/stats 重建的时间。
- `未分配`：串口包中存在未加入当前事件的接收机，不等于已映射接收机落库失败。
- CSV文件大小是长期累计值；“已写行数”是当前服务进程计数，两者不能直接相除判断行大小。

## 6. 禁止回退

- 不得让教练端和观众端分别维护两套永久统计真相。
- 不得恢复“在线30Hz实时 + 独立5Hz persistOnly”双发架构。
- 不得在刷新时只恢复最新尾部而丢弃完整历史。
- 不得让回补旧包更新当前摇杆、当前接收机在线状态或当前飞手映射。
- 不得在每个回补包后全量重建。
- 不得在ACK前删除IndexedDB记录。
- 不得静默吞掉IndexedDB写入/删除错误。
- 不得用本地开发数据库推断生产服务器数据是否存在。
- 不得把 Web Serial reader、JSON 分帧或采集时间戳重新移回 React/Window 渲染循环；不得用增大串口缓冲区代替持续消费，也不得在非致命读取错误后关闭整个串口。
- 不得声称普通网页能跨越浏览器“整页冻结/丢弃”、操作系统睡眠、USB拔出或进程终止继续采集。Dedicated Worker 解决的是后台标签页调度与渲染竞争；若浏览器冻结后系统仍保留串口字节，恢复时按硬件时钟补录。正式长时值守必须把采集站点加入浏览器节能/内存节省白名单，绝对不丢数据的部署应把串口采集迁到独立本地进程。

## 7. 修改后的最低验证

```bash
npm run lint
npm run build
npm run verify:serial-json-stream
npm run verify:training-live
npm run verify:live-load
```

真实环境还必须覆盖：

1. 持续飞行与待机条带无假缝，统计和跳秒稳定。
2. 刷新教练端、观众端后完整历史与服务器一致。
3. 训练中修改飞手时间、删除/新增飞手、迁移接收机后历史归属正确。
4. 断网期间教练端继续本地显示，观众端不伪造数据。
5. 恢复网络后当前画面立即恢复，旧缓存后台下降，回补累计落库增加，最近重建更新，最终两端缺口补齐。
6. 教练页面被其他标签页或窗口遮挡至少30分钟，串口仍持续读取；返回后不得出现旧摇杆快放，服务器样本除真实硬件/系统中断外不得产生超过1秒的新缺口。
7. 验收记录必须区分“hidden后台标签页”和浏览器主动 `freeze/discard`/系统睡眠。后者不能作为纯网页持续采集能力验收通过项，只验证恢复后能诊断、重连并按硬件时间补录尚在缓冲区的数据。

## 8. 已踩过的坑：症状、原因、守护边界

| 现场症状 | 已确认的原因 | 不可破坏的边界与回归证据 |
| --- | --- | --- |
| 正常联网飞行时条带出现细灰缝，刷新后仍在 | 服务器把同房间待处理的可靠帧当普通兜底帧合并，甚至对尚未写入 SQLite 的帧回 `accepted: true, sampled: false`；浏览器据此删掉 IndexedDB 唯一副本 | 只合并无 `packetId` 的普通兜底帧；可靠帧 FIFO 处理后才能成功 ACK；客户端对 `sampled: false` 一律不删除缓存。`verify-training-live` 中的可靠帧突发用例必须保持通过。 |
| 网络正常却缓慢累计“恢复/渐进/校准”，且条带愈来愈稀疏 | 服务器根据客户端时间与到达时间之差大于阈值，猜测在线可靠帧是回补；重建负担又加大延迟，形成反馈循环 | 只有协议 `backfill: true` 可以进入回补支路；不能用包龄、时钟偏差、后台状态或处理耗时推断。在线抖动用例要求这些恢复计数不增长。 |
| 飞行时补回旧数据后，新的实时样本短暂被判为待机 | 回补旧样本覆盖了在线飞手最近5秒内存窗口，下一条实时状态失去飞行上下文 | 历史回补只读写对应采集时刻的 SQLite 上下文，不修改当前窗口、当前接收机和广播时钟。在线飞行夹回补测试须保持连续。 |
| 页面被遮挡后串口 JSON 截断、缺历史；恢复后旧摇杆快放 | Window 渲染/计时器停摆或降频，串口读取和整批帧时间戳仍依赖它；非致命串口读取错误被当成断线 | Worker 持续读并按完整 JSON 分帧；硬件单调时钟保留积压帧原时间；旧帧只能显式回补，不能实时广播；非致命错误直接接新 `readable`。主线程兼容路径保留但不宣称同等后台能力。 |
| 短时网络波动恢复慢、看起来等一大段才补齐 | ACK、重连或前台唤醒时沿用后台已过期但尚未执行的发送泵定时器；或在线3秒 ACK 看门狗不断推迟25ms恢复泵 | 过期定时器必须能被立即唤醒替换；新的较晚请求不得推迟已排定的恢复泵；恢复旧包不挤占当前帧；渐进补丁与最终校准各司其职。 |
| 长时间待机冒绿缝或飞行出现灰缝 | 某个可靠帧因调度停顿，把数秒前的油门极值混入当前约200ms窗口；另一种原因是真实1秒以上缺口，不可混淆 | 极值只取当前帧附近最多500ms的原始数据；状态仍只由服务端固定规则判定。用原始样本时间、SQLite 间距及 `verify-training-live` 区分假缝和真缺口，绝不靠补色掩盖。 |
| 删除事件后孤儿缓存反复出现，或新事件沿用旧事件编号 | 旧包仍带创建时的事件ID；仅清掉某一批缓存而仍有旧事件生产者/页面继续写入 | 每包事件ID不可事后偷换；已删除事件的缓存应清理，生产者必须切换到有效活动事件。不得把旧事件包强行归入新事件来“修复”数字。 |

回归测试只证明对应协议不变量；本项目不能通过单元测试模拟真实接收阵列、浏览器后台策略和飞行操作。因此每次改动这些核心文件，必须记录“测试结果 + 真实环境可见条带/恢复结果”；未覆盖的环境和故障类型应明确写为未验证，不能泛称全部通过。
